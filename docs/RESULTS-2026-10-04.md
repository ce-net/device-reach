### 1 · A forward can be closed — ce branch `tunnel-close`

The node kept no record of the forwards it held, so `POST /tunnel` spawned an accept loop and
dropped the handle. The branch adds a tunnel registry on `ApiState`, `GET /tunnels`,
`DELETE /tunnel {"local_port": N}`, and a 409 on re-open that names the existing target instead
of letting the OS answer with "address already in use". The accept loop now waits on the close
signal and `accept()` together with `tokio::select!`, which is what actually frees the port: a
loop that only awaits `accept()` never wakes, and a flag checked after each accept would hold
the port until the next connection arrived.

(macOS) PASS, Boundary gates PASS. The seven new tests, read out of the job log:

### 2 · `huey:8940` is a real address

`ce-iam name bind` had zero bindings. There are two now, 365 days each:

```
huey -> 75ccba6e3540f4e550fa59936944b0464e02d2ea348cdfc0023659cdcf57c26d
mac  -> 0e95015b2d034b3c973e1fe22e2e811067c409daa24e01ac8d9eadb1543ed493
```

device-reach reads signed bindings as a third device source. A binding that disagrees with a
table keeps the table's node id and leaves a note on every answer: a disagreement is a fact to
look at, not a tie to break quietly. A device known only from a binding declares no ports, not
even ssh, because a binding says which node a name is and never what that node serves.

A per-device IP needs root on macOS — a loopback alias, `/etc/hosts` and `/etc/resolver` all do.
Asking for root to read a leg angle is the wrong trade, so the daemon runs a name proxy on
127.0.0.1:8944 instead and any proxy-aware client gets real device addresses with no privileges:

```bash
http_proxy=http://127.0.0.1:8944 curl http://huey:8940/api/state
ssh -o ProxyCommand='nc -X connect -x 127.0.0.1:8944 %h %p' arduino@huey
```

Measured: `http://loop:8943/api/health` returned the daemon's own JSON through the plain path
and through `CONNECT`, `.ce` and `.mesh` suffixes resolved to the same device, and an unknown
name returned `502 no device named 'nope' (known: huey, mac)`. The remaining gap is stated in
the README: a client that ignores `http_proxy` still needs the loopback port.

Huey went off the network at about 22:20 (ping 100 % loss, ssh reset by peer, nothing on :8940
over LAN or mesh), so the proxy was measured against a local upstream and against the daemon
itself. `huey:8940` wants one re-measurement against the board when it is back.

### 3 · The path behind a number — ce branch `netgraph-path`, and `reach path`

The relayed measurement could not be taken as planned, and the reason is worth more than a
guess would have been. Two things were in the way, and the first is now fixed.

**The node could not say.** `/netgraph` reported a peer's RTT and threw away the address it was
measured over, so a relayed 128 ms looked exactly like a direct one. libp2p knows — a circuit
address carries a `/p2p-circuit` hop — the node just did not keep it. Branch `netgraph-path`:

the connection closes so a stale "direct" cannot outlive the connection that earned it. The same

mesh; the row serializes `null` while `samples` is 0.

### 5 · Datagrams — `reach udp` and `/ce/udp/1`

`/ce/tunnel/1` splices TCP, so every datagram protocol was out: DNS-SD discovery, NTP, syslog,
an OSC controller, most telemetry. A byte stream cannot carry them honestly — a 1472-byte
packet followed by a 68-byte packet must arrive as two packets, and a splice delivers one
1540-byte blob.

So the mesh gained a second protocol beside the first, `/ce/udp/1`, with the same authorized
header, so the same `tunnel` capability covers both and no new grant is needed. Each datagram
is length-prefixed on the wire. One larger than 65507 bytes is refused rather than split; an
idle flow is dropped after 120 s so a port scan cannot pin memory.

Node side, branch `udp-tunnel` of the `ce` repo, stacked on `tunnel-close`:

| | |
|---|---|
| `ce_mesh::UDP_PROTOCOL` | `/ce/udp/1`, plus `UDP_MAX_DATAGRAM = 65_507` |
| `read_header_and_authorize` | pulled out of the TCP path so both protocols authorize identically, rather than twice with a drift between them |
| `POST /udp-tunnel` | binds a loopback `UdpSocket`, one mesh stream per peer flow |
| `GET /tunnels` | now carries `proto`, so a row says which kind of forward it is |

CI, run [37211918360](https://github.com/ce-net/ce/actions/runs/37211918360), macOS Test job:
**4 `udp_tunnel.rs` integration tests and 5 `udp_frame_tests` unit tests passed, 0 failed**, and

`ce-iam revoke --nonce <n>` fails: *"submitting revocation to http://127.0.0.1:8844: node
error: decoding revoke response"*. The node's `POST /capabilities/revoke` answers
`401 {"error": "missing or invalid API token (send Authorization: Bearer <data_dir>/api.token)"}`,
and ce-iam tries to parse that as the success shape instead of printing the sentence it was
given. The same call with the token attached returns `201 {"directed": true}` and the nonce
appears in `GET /capabilities/revoked`. So revocation works and its only CLI does not, which
matters because revocation is the thing that makes a capability safer than a key. Measured
2026-10-04 22:00 CST; the workaround is the curl above.
