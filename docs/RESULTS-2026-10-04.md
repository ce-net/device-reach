## The one command

```
$ reach get huey walk /api/state
{"app": "huey.walk-command", "mode": "manual", "stopped": false, "last_cmd": {...}}
```

No host, no IP, no port, no key typed. `huey` is a name; `walk` is a name; the path is a libp2p
stream to the UNO Q's own loopback, opened by the local ce node and allowed only by a `tunnel`
capability for that board.

## Latency, measured 2026-10-04 22:05 CST, TroubleMaker Wi-Fi

30 GETs per row, `curl -s -o /dev/null -w '%{time_total}'`, sorted, p50 and p90 read off.

| path | endpoint | p50 | p90 | min | max |
|---|---|---|---|---|---|
| **ce-net** | `127.0.0.1:18938/api/bus` (servo bus) | **47.4 ms** | 119.8 ms | 20.5 | 168.2 |
| LAN | `192.168.1.x:8938/api/bus` | 52.9 ms | 96.3 ms | 20.8 | 196.6 |
| **ce-net** | `127.0.0.1:18940/api/state` (walk door) | **40.5 ms** | 67.7 ms | 22.4 | 819.8 |
| LAN | `192.168.1.x:8940/api/state` | 60.0 ms | 133.2 ms | 24.3 | 1041.7 |

**The overlay costs nothing measurable here.** Both devices are on one Wi-Fi, so the mesh path
is a direct libp2p connection, not a relay. The spread is the UNO Q answering, not the network:
`time_connect` to the loopback forward is 0.3 ms and to the LAN address 5–87 ms, while
`time_total` is 20–200 ms on both.

Opening a forward that did not exist: **0.04 s**, and the first GET through it answered 200 in
74 ms. There is no warm-up penalty worth naming.

A `reach ping` of the same endpoint, through the tool rather than curl:

```

  n=30 answered=30  p50 42.8 ms  p90 72.1 ms  min 20.9  max 248.0
```

## The second device: Huey reaches the Mac back

The board is not only a target. `reach` is 350 lines of stdlib Python, so it runs on the UNO Q
itself (Python 3.13.5, aarch64 Linux). With a `tunnel` grant for the Mac in the board's ce
wallet and a two-line `devices.json`, the duck reached the Mac's **loopback-only** daemon by
name:

```
arduino@huey$ reach get mac reachd /api/health
{"app": "net.device-reach", "version": "0.1.0", "ok": true, ...}

arduino@huey$ reach ping mac reachd --path /api/health -n 30
mac reachd over ce-net (http://127.0.0.1:18943/api/health): PASS
  n=30 answered=30  p50 37.5 ms  p90 105.3 ms  min 16.9  max 265.5
```

Nothing on the Mac listens on anything but 127.0.0.1. The overlay is what made it reachable,
and it is symmetric.

## The ACL works, with a positive control

The grant the board held was minted `--allowed-port 8943`. From the board, in the same minute,
against the same Mac:

| grant | remote port asked for | answer |
|---|---|---|
| `--allowed-port 7799` | 7799 (the launchpad) | **HTTP 200** |
| `--allowed-port 8943` | 7799 (the launchpad) | **nothing** |

Same device, same port, same moment: the only difference is which port the capability allows.
The local listener binds either way, because the local node is not the enforcer; the Mac's node
is, and it refused the stream. The 7799 grant was then removed from the board's wallet and
revoked (nonce 64211, now in the node's revoked set of 67).

### One measurement note worth keeping

Python's `urllib` against the LAN address read p50 1009 ms, with every sample within 40 ms of
exactly one second, while curl against the same URL in the same minute read p50 52.9 ms. The
same `urllib` through the loopback forward read 42.8 ms. A clean one second is a timer, not a
network, and the likely culprit is a delayed-ACK interaction on the board's Wi-Fi stack for

## The authorization door, broken on purpose

`POST /api/up` is gated on the literal action `device-reach:up` through `ce-py/cegate.py`.
Four states, measured 21:44–21:46:

| what was presented | answer |
|---|---|
| nothing | `401 no_capability` — "no capability was presented", with how to mint one |
| `Content-Type: text/plain` | `415` — cegate checks the transport before the capability |
| a grant for `device-reach:up` | `200`, forward opened, `by: cap:0e95015b2d034b3c@http:127.0.0.1` |
| that same grant, on `/api/down` | `401 denied: capability does not grant 'device-reach:down'` |
| the gate removed from the handler | `503 no_authorization_gate`, naming the reason |

The last row is a test (`tests/test_reach.py::GateRefuses`), not a story: it deletes the gate and
asserts the route refuses.

## What is still missing, in the order it should be fixed

1. **Close a forward.** The ce node keeps no tunnel registry and exposes no close route
   (`ce/crates/ce-node/src/api.rs`, `open_tunnel`). Until then a granted forward lasts until the
   node restarts, and `reach down` says so. This is the single highest-value change to the core.
2. **Names from the mesh.** `ce-iam name bind huey <node id>` exists and holds zero bindings;
   today `huey` is a key in a JSON file on this Mac only.
3. **A per-device address**, so the local port can equal the remote one and `huey:8940` works
   unchanged. Needs a loopback alias (root) plus the name binding.
4. **A relayed path.** Both devices measured are on one Wi-Fi, so both directions were direct
   libp2p. Nothing here proves the relay fallback; a run from the Hetzner box would settle it.
5. **A policy file** instead of grants minted one at a time, and default expiries.

## One defect found on the way, not fixed here

`ce-iam revoke --nonce <n>` fails: *"submitting revocation to http://127.0.0.1:8844: node
error: decoding revoke response"*. The node's `POST /capabilities/revoke` answers
`401 {"error": "missing or invalid API token (send Authorization: Bearer <data_dir>/api.token)"}`,
and ce-iam tries to parse that as the success shape instead of printing the sentence it was
given. The same call with the token attached returns `201 {"directed": true}` and the nonce
appears in `GET /capabilities/revoked`. So revocation works and its only CLI does not, which
matters because revocation is the thing that makes a capability safer than a key. Measured
2026-10-04 22:00 CST; the workaround is the curl above.
